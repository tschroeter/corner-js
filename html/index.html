Continuous corners for the web

The corners
CSS cannot draw

A squircle is neither a rounded rectangle nor a circle — a few pixels of silhouette that change how the whole shape reads. It is not new: Piet Hein named it in 1959 and built a Stockholm square out of it, and the curve behind it is two centuries old. Screens got it late — Nokia in 2011, then iOS 7 made it everyone's. Apple's own corner is not even a squircle: an arc with Bézier shoulders that no superellipse exponent reaches, which is what Figma's construction reproduces. corner.js draws both as a clip-path, shadow and border on the same path.

Features

What you get

Five things it does, each one checkable further down.

  • One attribute. data-corner-js on the element, and nothing else — no component, no import, no call.
  • The shadow and the border follow the curve. A clip-path removes both from the element it clips, so both are rebuilt along the exact path that was drawn.
  • The shape comes out of your CSS. border-radius, --corner-smoothing and box-shadow are read where they already are. Nothing is declared twice.
  • It works inside your framework. React, Vue, Solid and Turbo are mounted and measured further down this page — in this browser, on every load. Svelte and Angular the same way, and there is nothing to add for any of them.
  • Progressive enhancement, literally. The corner is the enhancement: with no JavaScript what shows is the border-radius you declared — and the corner-shape, in a browser that has it. No empty box, no layout shift.

Using it

Integration

The shape is declared in markup, so whatever renders the markup is enough — your framework included. On a plain page that is the entire integration.

Plain HTML — and Turbo, htmx, Astro, any server render
<script async src="corner.min.js"></script>

<div class="card" data-corner-js>…</div>

A mount, a hydration and a swapped fragment are the same event to a MutationObserver, so nothing needs hooking. Inside React, Vue, Svelte or Angular, Solid or Turbo there is one thing to do, and it is not about drawing: render the wrapper yourself. Four of those six are mounted and measured at the end of this section, in this browser, every time the page loads.

corner.js moves every drawn element into a wrapper <div>, because the shadow and the border are redrawn as siblings and need an ancestor that is not clipped. The reconciler, meanwhile, still holds the parent it rendered into — measured in Chrome, removeChild and insertBefore then both throw NotFoundError. An element already inside [data-corner-shadow-wrap] is left where it is, so the tree the framework owns stays untouched.

React
import cornerjs from 'corner.js'
import { useEffect, useRef } from 'react'

export function Card ({ children })
{
    const ref = useRef(null)

    // The observer would draw it a microtask later;
    // apply draws it now.
    useEffect(() => { cornerjs.apply(ref.current) }, [])

    return (
        <div ref={ref} data-corner-shadow-wrap
             style={{ position: 'relative' }}>
            <div className="card" data-corner-js>
                {children}
            </div>
        </div>
    )
}

One detail every one of those shares: the wrapper has to be positioned, because the shadow SVG anchors to the nearest positioned ancestor. The element inside keeps whatever size its own CSS gives it — corner.js does not resize it, and it only puts an element in a wrapper at all when a shadow or a border has to be redrawn.

With a bundler, import instead of reaching for the global: import { apply, refresh } from 'corner.js'. The built file is for a <script> tag and sets window.cornerjs; the module source is what npm resolves.

apply(root) is not required for the corner to appear — the observer draws it either way, a microtask later. It matters when the component measures itself on mount, since it draws synchronously. It returns how many elements it started, and a root counts as a target only if it carries the attribute itself.

refresh(root) is for a style change, which no ResizeObserver reports: a radius or smoothing edit alters the shape, not the box. Pass { reread: true } when box-shadow or border changed as well. Size changes need neither, and neither does changing data-corner-js: the observer sees the new value and redraws the element in the new curve.

What it costs

Limitations

Most of these are what clip-path does, not choices — anything that clips inherits them.

  • Everything inside the element is clipped — children, overflow, pseudo-elements, a scrollbar. A tooltip or dropdown that leaves the box is cut at the curve. It is the same clip that draws the shape.
  • Focus rings are cut with it. Put the focus style on a parent rather than on the clipped element.
  • The inserted wrapper becomes the flex or grid item. Percentage sizes, fixed dimensions and parent > child selectors stop behaving; real dimensions have to go on the wrapper.
  • Only the top border is read. Width, colour and style come from border-top-*: one continuous curve has no sides to give four different strokes to.
  • One form of border-radius is not understood. Everything the cascade resolves to a length arrives correctly — four different corners, em, var(), inherit, calc() of lengths. A percentage is elliptical by definition and is resolved against the width, like a declared elliptical radius. But a calc() that mixes a percentage with a length stays unresolved in the computed value and reads as 0 — a square corner, drawn without complaint.
  • Only solid borders. One stroke along the path — no dashed, dotted or double, and no border-image.
  • outline is left alone, which means it is clipped rather than redrawn along the curve.
  • The shadow and border are read once. They have to be cached: by the second run getComputedStyle would read back corner.js's own overrides. A later stylesheet change needs refresh(root, { reread: true }).
  • !important beats the strip. The element's own box-shadow is cleared with an inline style, so a rule marked important outranks it and both shadows paint.
  • No transitions on shadow or border. Both are replaced by SVG, so a CSS transition on them has nothing to animate. The clip is not animatable either.
  • A document-wide MutationObserver stays running, so corner.js gets a callback on every DOM mutation on the page. It bails out early for non-elements and subtrees with no targets, but it is not free. The trade is that nothing has to boot it.

How it is drawn

What draws which curve

Not a hierarchy to descend. For the continuous curve there is exactly one technique and no alternative; a real fallback relationship exists only for the two superellipse modes. The column that applies to you is marked.

You ask for With corner-shape Without it JavaScript off
continuous clip-path — no CSS value expresses this curve clip-path border-radius
squircle native, GPU, no JavaScript clip-path border-radius
superellipse-5 native, as superellipse(log₂5) clip-path border-radius

–

No exponent of the superellipse reaches the continuous curve, and that is measured rather than assumed: Figma checked the fit against the real icon and found “a small but systematic discrepancy” at every exponent (Desperately seeking squircles). Which is why they derived a construction with a parameter instead of fitting one number.

A Houdini paint worklet could draw either family exactly — it is a canvas, not a vocabulary. Not implemented, and not planned, because its availability is disjoint from where it would help: the API is Chromium-only, and Chromium is also the only engine with corner-shape. It would speed up the one browser in which clip-path already works, and be absent from the two where a faster path would be worth having.

Native corner-shape is Chromium-only too, and is used anyway, which looks inconsistent until you price the two. Supporting native is not an implementation but an early return: one CSS.supports check and the module steps aside, so the GPU draws it for free where it exists and the existing path runs where it does not. A worklet would be a second full implementation — its own file, its own registration, masking instead of clipping with its own shadow and border consequences — for a browser that already works. One if against a parallel code path.

The chain, in order. A continuous corner needs clip-path and has no substitute for it: without it the declared border-radius stands, which is the last resort for every row above. A superellipse has one rung more — native corner-shape where it exists, a clip-path where it does not, border-radius if neither.

Where clip-path draws, the shadow and the border are drawn as SVG beside it, because a clip removes the element's own. That is not a tier — it is the consequence of clipping, and it applies in every browser.

The curve itself

The shape

What curvature continuity is, which two families have it, and why Figma needed a construction with a parameter rather than one exponent.

Two curve families provide continuous curvature: the superellipse, whose exponent 4 case is the squircle, and an arc with Bézier shoulders, which is what corner.js draws.

Two curves can meet three ways: at a point (a sharp corner), sharing a direction (tangent continuous — what border-radius gives you, with curvature jumping from 0 to 1/r), or sharing curvature too (curvature continuous — this). Draftsmen write those G0, G1 and G2.

Apple's corner is, in Figma's own words, a patchwork of Bézier curves spliced together — not a formula, so it cannot be turned down for something long and thin. They derived a construction with a parameter instead, and that parameter is smoothing. The code here follows phamfoo/figma-squircle's port of that derivation, verified term by term.

Both inputs come from CSS, and --corner-smoothing inherits: set it once on a container. Smoothing controls two things at once:

  • the corner's reach along each edge, p = (1 + smoothing) × radius;
  • how much of the 90° stays a circular arc, 90 × (1 − smoothing).

At radius 32: 0.6 reaches 51.2px, 0 reaches 32px with a full arc, 1 reaches 64px with none.

The reach is also what runs out. Two corners on one side want 1.6× that side at 60%, so capping the radius alone is too generous by that factor: past it the path ran backwards and notched each long edge. Roundness is spent first and smoothing gives way, so a capsule end stays clean. The Derived panel reads the values back out of the drawn path.

ExponentNameIn CSS
2Circle — identical to border-radius round, or superellipse(1)
4Squircle — Piet Hein's case squircle, or superellipse(2)
5No established name. The closest single exponent to Apple's curve, and still off superellipse(2.3219)

The CSS parameter is not the exponent, which is the easiest thing here to get wrong: it is its base-2 logarithm. Measured in this browser, superellipse(1) computes to round and superellipse(2) to squircle — a circle is exponent 2, so the keyword is exponent 4. A squircle is not exponent 5.

InputDefaultMeaning
border-radius — Corner size. Read as the construction's input, not merely as a fallback. Per-corner values are honoured.
--corner-smoothing 0.6 How much of the corner is a Bézier ramp rather than a circular arc. Inherits.
.corner-continuous — Selects this construction. Without it the element gets a superellipse (n = 4, the squircle), or n = 5, and defers to native corner-shape where that exists.

Along the same path

The shadow

clip-path clips away box-shadow on the same element, and filter: drop-shadow with it. The shadow therefore cannot live on the clipped element.

It is drawn as its own SVG along the same path, as a sibling inside a [data-corner-shadow-wrap] wrapper. A rounded rect on the wrapper was tried first; its circular corners visibly miss the continuous curve.

Built from the element's own computed box-shadow, per layer:

CSSSVG
blur bfeGaussianBlur stdDeviation="b / 2" — a CSS blur radius is two standard deviations
spread sfeMorphology dilate/erode with radius |s|, before the blur
offsetfeOffset
colourfeColorMatrix to that layer's actual RGB and alpha
layer ordermerged in reverse — box-shadow paints the first layer on top, feMerge the last node

Its size comes from the shadow's reach (1.5 × blur + offset + spread), not a fixed margin.

Three consequences:

  • Transform the wrapper, not the target. A transform on the target leaves the SVG behind.
  • The target is no longer a direct child. A parent > target selector stops matching after boot.
  • A percentage size resolves against the wrapper, which is auto. Put real dimensions on the wrapper.

Measurement uses the layout box, never getBoundingClientRect(): the rect includes ancestor transforms and everything drawn lives inside that same subtree, so the scale would apply twice. A 500px box at scale(0.97) got a 485px shadow.

History

Neither circle nor rectangle

Not Apple, not Figma, not corner.js. The shape is two centuries old, the word is sixty, and the reason anyone cares about curvature continuity comes from car bodies rather than from screens.

  • 1818 — Gabriel Lamé. The curve itself: raise the exponent in a circle's or ellipse's equation above 2 and it swells towards a square. Every superellipse here is a Lamé curve, and the exponent-4 case centred on the origin is Lamé's special quartic. The family is worth seeing whole: at exponent 1 it is a diamond, at 2 the circle or ellipse, and as the exponent grows it approaches a rectangle — one equation and one parameter from sharp to round.
  • Mid-century — car surfacing. The reason curvature continuity matters at all was found on sheet metal, not on screens. A flat panel running into a radius means the curvature jumps from 0 to 1/r at one line, and on a reflective surface that line is visible: a perfect mirror abruptly becomes a stretched one. Surfacers check it with curvature combs — spaced lines drawn perpendicular to the curve, each as long as the curvature at that point. Combs that meet at the join are acceptable; combs tangential to each other are better; and the same test can be applied to the comb's own rate of change. None of this is specialist knowledge in product design, and type designers work to it too, often by eye rather than by arithmetic.
  • 1960s — Pierre Bézier, at Renault. The corners here are cubic Béziers, and they came out of the same industry. Bézier spent decades at Renault and developed them for car body design; Paul de Casteljau was working out the same mathematics at Citroën around the same time. The web draws rounded corners with a tool built to draw fenders.
  • 1959 — Piet Hein. Named it and put it to work: superellipse for the general case, supercircle when the axes are equal. He was not after a new family of curves but a specific problem — Sergels Torg in Stockholm needed a form that held the square together without being static as a circle or hard as a rectangle. What he arrived at is exponent 5/2 with axes at 6:5, and the fountain is still that shape. He carried it on into tables, furniture and jewellery.
  • 1966 — Peter Panholzer. Coined squircle, as an architect working for Gerald Robinson, after Robinson read Piet Hein in Scientific American and suggested the shape for a project. Panholzer drew fifteen of them by hand on vellum over graph paper, from exponent 2.6 to 4.0, and surveyed which people preferred: about 3.1. He then computed the exponent whose area sits exactly halfway between the circle's and the square's — 3.1620, close to π but not π — and had a conference table built at it. Robinson, for his part, designed a parking garage at exponent e.
  • 2011 — Nokia. Used the shape as an identity rather than a detail: many Nokia handsets carry a squircle touchpad button, and MeeGo's Harmattan built its whole icon language on it — documented by the community that reverse-engineered the grid, in The squircle design philosophy, rather than in a published Nokia specification.
  • 2013 — Apple. Shipped a continuous corner across the platform, which is where the idea that a corner could be something other than a quarter circle stopped being a specialist concern. It is not a superellipse: it keeps a circular arc at the apex with Bézier shoulders either side, and Apple's own name for it is continuous. On the exponent, the sources are about different things rather than in conflict. Wikipedia calls the icon shape an approximation of a squircle that is actually a quintic superellipse — quintic meaning fifth degree, so exponent 5, not the squircle's 4. The word itself is not settled either: Cook notes that some sources define the squircle as p = 4 and others as p = 5, and reports exponent 4 in some other Apple designs. Neither is the corner style itself, which is not a superellipse at all: that is the whole reason Figma stopped fitting exponents to it. Grida's write-up says the same and adds a heuristic for the other direction, n(s) ≈ 2 + 8s², which puts 60% smoothing near exponent 4.9 — so the two shapes land close together at the setting everyone uses, while remaining different constructions.
  • 2018 — Figma. Could not fit a single exponent to Apple's curve, so they derived a construction with a parameter instead of tracing a path. That parameter is corner smoothing, and it is the reason the shape can be turned down for an element that is long and thin. Their working also produced a clothoid — the curve that bends at a constant rate, which is why roads are laid out with it — and they dropped it: turning the smoothing up made the corner's arc drift rather than stay put, and the shape needed segments more complex than the cubic Béziers their renderer draws.
  • 2025 — CSS. corner-shape puts the Lamé family into the platform: squircle is exponent 4, and superellipse(k) takes any exponent as 2k.
  • corner.js. Draws Figma's construction where CSS cannot, and steps aside where it can. A curve from 1818, a name from 1966, a criterion from the paint shop, a parametrization from 2018: none of it is ours.

How much this matters depends on the dimension, and it is worth being honest about which one a web page is in. In 2D, tangent continuity is usually enough: a square rounded with quadratic arcs, with cubic ones, or with a superellipse all look fine, and the difference is easier to see than to name even when you can see it. It is in shaded 3D that curvature discontinuity becomes glaring — the artefact is called broken highlights, and CAD packages ship zebra-stripe analysis specifically to hunt for it before a surface goes to tooling. So a continuous corner on a screen is a refinement, not a rescue.

The same order of continuity turns up wherever a smooth appearance is computed rather than drawn. Smoothstep is only C1 continuous, which is why a displacement or bump shader built on it can still show a seam; Perlin's own improved variant is C2. Two notations are in circulation for this and they are not interchangeable: C for parametric continuity, G for geometric.

On sourcing. The curve, the quartic, Nokia's button and Apple's approximation are from Wikipedia and Apple's own documentation. The 1966 coinage and the 3.1620 figure rest on a single account, John D. Cook's, written after Panholzer contacted him with his evidence; there is no published paper behind it, and it is here on that footing rather than as an established fact.

Questions

Continuous curvature,
answered

How do I get squircle corners in CSS?

That depends on which curve you mean, and the difference is the point. A squircle is a superellipse: where the browser has corner-shape, one declaration does it, border-radius: 20px; corner-shape: squircle — corner.js only fills in where that property is missing, drawing the same curve as a clip-path. The Apple-like continuous corner has no CSS equivalent in any browser, so data-corner-js always draws. Either way the shape comes from the border-radius already in your stylesheet.

What is the difference between a squircle and Apple’s corner?

A squircle is a superellipse, |x|4 + |y|4 = 1. Apple’s corner is not a superellipse at all: it is a circular arc with a cubic Bézier shoulder either side, which is why no single exponent reproduces it. By the definition, then, Apple's corner is not a squircle: it is a curvature-continuous corner — G2 to a draftsman. Figma reached the same conclusion by measuring the shape and publishing the attempt — Desperately seeking squircles — and derived a construction with a smoothing parameter instead of fitting one exponent. That construction is data-corner-js here.

What does corner smoothing actually do?

It splits the 90° of a corner between an arc and two Bézier shoulders. --corner-smoothing: 0 leaves the whole angle as an arc, which is plain border-radius; 1 leaves no arc at all. Figma’s value for the Apple-like shape is 0.6, and it is the default here.

Does corner-shape work in Safari and Firefox?

Not yet — it is Chromium-only. The support table above measures the browser you are reading this in rather than quoting a version. corner.js is the fallback for the other two, and steps aside where the property exists.

Why does my box-shadow disappear on a squircle?

Because clip-path removes box-shadow and filter: drop-shadow from the element it clips, and halves the width of its border. corner.js redraws both as sibling SVGs along the same path — which is why every drawn element is moved into a wrapper <div>: the siblings need an ancestor that is not clipped.

Is there a React, Vue or Svelte binding?

No package and no boilerplate — plain vanilla JavaScript, inside all of them, and React, Vue, Solid and Turbo are mounted and measured live on this page. Drawing is not the hard part: data-corner-js in JSX or a template is enough for that, since nothing is encapsulated and the attribute lands in the real DOM.

What matters is who owns the parent. corner.js moves every drawn element into a wrapper <div>, while the reconciler still holds the parent it rendered into — measured in Chrome, both removeChild and insertBefore then throw NotFoundError. So inside a framework subtree, render the wrapper yourself — it is reused, not replaced — and call apply on the container after mounting. 

<div data-corner-shadow-wrap style="position: relative">
    <div className="card" data-corner-js>…</div>
</div>

useEffect(() => { cornerjs.apply(ref.current) }, [])

The wrapper has to be positioned, because the shadow SVG anchors to the nearest positioned ancestor. The element keeps its own size, and it is only moved into a wrapper when a shadow or a border needs redrawing. See Integration.

Can I animate or resize an element with a drawn corner?

It depends on what is moving. Transform and opacity: yes, with nothing to do — the path is measured in the layout box, which a transform does not touch, and it scales as vector along with the element. Size: yes — every element carries its own ResizeObserver, so a width or height animation redraws the path, the shadow and the border per frame.

An animated border-radius does not follow. Nothing observes a style change: the box is unchanged, so no callback exists. The only two things watched are the box and the data-corner-js attribute. Drive it yourself — cornerjs.refresh(el) per frame is what the sliders above do on every input event.

What is a superellipse, and who invented the squircle?

The curve is Gabriel Lamé’s, from 1818. The shape was popularized by Piet Hein for Stockholm’s Sergels torg in 1959, and the word “squircle” is younger than either. History has the sources.
